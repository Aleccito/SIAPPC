# Session digest — 2026-07-24

Origin of this project and the reasoning behind its choices. Written so a future
reader (human or agent) does not have to re-litigate settled decisions.

## What was asked

A modular internal web app. Frontend first: a login page and a main page, white
palette. Later: MariaDB in Docker, an embedded Power BI screen, and FlexSim
integration. The opening question was whether React was the right pick.

## How the stack was chosen

A five-advisor council was run on the question. All five converged on the same
load-bearing points:

- **React, yes** — not on merit alone, but because `powerbi-client-react` is
  first-party Microsoft. Vue and Angular were viable; React had more precedent
  for this exact combination.
- **No Next.js.** An internal app behind auth gains nothing from SSR and
  inherits deployment weight.
- **A backend is needed sooner than "phase 2" implies.** Embed tokens and
  database credentials cannot live in the browser. Not a preference — a
  constraint.
- **FlexSim is asynchronous batch, never live.** It is a Windows desktop
  application with no web API.
- **Power BI licensing is a real, unresolved cost** and must be confirmed
  before the dashboard screen is designed.

Where they disagreed: whether to build the frontend at all before the schema
and integrations were proven. The Skeptic and Contrarian wanted a freeze; the
Optimist wanted to ship. Resolution taken: build phase 1 now, because login and
shell are schema-independent, but do not build data tables against a guessed
schema, and prove the two integrations in parallel.

The Contrarian's alternative — server-rendered HTML with HTMX instead of an SPA
— was considered and rejected only because React was already the user's
direction. It remains a defensible option if the app stays a thin shell.

## Two open questions that block phase 2

Neither was answered during this session. Both change architecture.

1. **Which Power BI SKU does the organisation own?** Per-user Pro/PPU versus an
   F/EM capacity. This determines the entire embed flow.
2. **Can FlexSim run headless on a controlled machine and write to a database?**
   Needs one dummy run to prove.

## What was built

Phase 1, frontend only, six modules. Every backend call is a fake with the real
signature — the swap points are listed in the README.

Order of work: Vite scaffold → auth shell and login → Power BI and Reports
modules → sanity pass → roles and admin screen → FlexSim module.

## Decisions worth not revisiting

- **MUI replaced Mantine.** The council recommended Mantine, but the user asked
  for free MUI icons, and `@mui/icons-material` requires `@mui/material` as a
  peer. Two component libraries and two theme systems for one icon set is not a
  trade worth making.
- **`powerbi-client-react` is deliberately not installed.** Without a backend
  embed-token endpoint it can render nothing. The page holds a marked
  placeholder; the drop-in is roughly fifteen lines.
- **One role per user, not a set.** `roles[]` only pays off with real permission
  composition, which does not exist here.
- **Fake login stores in `sessionStorage`, not `localStorage`** — narrower XSS
  window, dies with the tab. The real token belongs in an httpOnly cookie.
- **The FlexSim fake derives status from elapsed wall time** rather than running
  timers. Runs progress realistically with no cleanup logic.

## Findings from the sanity pass

Two real defects, both fixed:

1. An unknown URL hit React Router's default ErrorBoundary and rendered the
   "Hey developer" dev screen. Fixed with a catch-all route.
2. `AuthProvider.tsx` carried an `eslint-disable` directive while the project
   uses oxlint and has no eslint config — the directive was inert, and the
   underlying mixed export forced full page reloads on every auth edit. The
   context moved to its own file.

Three things were checked and deliberately left alone: the `NavLink to="/"`
"always active" bug does not occur in React Router v7 (verified in the browser,
not assumed); `JSON.parse` on stored user only throws if someone hand-edits
storage; the icons barrel import is type-only and erased at compile.

## Verification approach

Nothing here was reported as working without being exercised in a browser:
type-check, lint, production build, then the actual flow — deep-link redirect
preserving its target, both role paths including a non-admin hitting
`/admin/users` directly, a role change persisting through a refetch, and the
FlexSim run lifecycle sampled once per second across its full
queued → running → completed transition.

One environment note that cost time: the FlexSim polling test first appeared
stuck on `queued`. The cause was the browser pane being hidden, which makes
TanStack Query pause interval refetching by design. Not a bug. Overriding
`document.visibilityState` in the console unpauses it for testing.

## Session conventions

The user ran with caveman-ultra brevity, the Karpathy guidelines (surgical
changes, no speculative abstractions, verifiable success criteria), and a
work-ethics secret scan active throughout. No secrets were ever committed; all
fixture emails use a fake domain.
